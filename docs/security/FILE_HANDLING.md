# File Handling Security

Status: ASVS 5.0.0 V5 assessed

## Scope

Journeyman does not provide an end-user file-upload feature. Automation content
is obtained from administrator-configured Git repositories, and repository
artefacts are generated by Journeyman from an immutable Git commit before being
dispatched to an authenticated runner. This distinction is important when
interpreting the ASVS upload controls in V5.1 and V5.2.

The file-handling security boundary that *does* apply to Journeyman includes:

- construction of repository, inventory-snapshot and runner-artefact paths;
- creation of temporary and immutable files containing execution data;
- creation and download of repository archive artefacts;
- extraction of repository archives by remote runners; and
- HTTP download filenames and `Content-Disposition` handling.

## Path construction

Paths used for application-managed repositories and runner artefacts are built
from trusted internal identifiers and resolved beneath configured application
roots. User-supplied display names are not used as filesystem paths.

Where a configurable path is intentionally supplied by an administrator, such
as an Ansible configuration path, Journeyman validates that input according to
the semantics of the field rather than concatenating it into a command or
filesystem root.

Path traversal must fail closed. Tests cover attempts to use `..` components
and repository identifiers that would resolve outside the configured root.

## Repository artefacts

Remote-runner repository archives are not uploaded by a browser user. They are
created server-side with `git archive` from the immutable repository commit
recorded in the Job repository snapshot. Artefact filenames are generated from
internal snapshot IDs and validated hexadecimal commit IDs, not from repository
names or request parameters.

The runner verifies both the expected archive size and SHA-256 digest before
extracting an artefact. Extraction is constrained to the runner workspace:

- archive members resolving outside the destination are rejected;
- symbolic links and hard links are rejected; and
- special files such as devices and FIFOs are rejected.

Only regular files and directories are extracted. This prevents traversal and
archive-link attacks such as Zip Slip/tar path escape even if an invalid archive
reaches the runner.

## Storage permissions

Sensitive generated data such as inventory snapshots, runner execution files,
credential material and temporary private data must be created under protected
application-controlled directories and with restrictive file permissions. The
specific secret-storage controls are also covered by
`docs/security/DATA_PROTECTION.md` and `docs/security/CRYPTOGRAPHY.md`.

## Downloads

Repository artefact download endpoints are authenticated runner APIs. The
requested Job/slice and repository snapshot are looked up by integer database
IDs and authorization/dispatch-token checks are performed before a file is
served. The download filename is generated by Journeyman and is passed to
Flask's `send_file(..., as_attachment=True, download_name=...)`; request or
repository display names do not control the `Content-Disposition` filename.

## Features not present

Journeyman currently has no generic browser file upload, image upload, archive
upload, or end-user file download facility. ASVS controls dealing specifically
with uploaded file type detection, upload quotas, decompression limits for user
uploads, image pixel-flood protection, upload symlinks, and antivirus scanning
of user-supplied downloadable files are therefore recorded as Not Applicable.

If any future feature accepts files from users or exposes files to end users,
all V5 applicability decisions must be reviewed before that feature is released.
