# Cryptography

This document records Journeyman's cryptographic inventory and the current
key-management boundary for the ASVS 5.0.0 assessment. Cryptographic choices
must use maintained, industry-standard libraries rather than application-defined
algorithms.

## Cryptographic inventory

| Purpose | Primitive / library | Key or secret | Storage / lifecycle |
| --- | --- | --- | --- |
| Credential, directory bind-password, Package secret and related encrypted fields at rest | `cryptography.fernet.Fernet` (authenticated encryption) | `JOURNEYMAN_CREDENTIAL_KEY_FILE`, normally `/etc/journeyman/credential.key` | Persistent host-managed key outside the database and repository. File must be a regular file and mode 0600 or stricter. Backed up separately from the database. |
| Remote execution-data envelope | AES-256-GCM via `cryptography` | Per-dispatch 256-bit key derived with HKDF-SHA256 from a high-entropy dispatch token and fresh random salt | Ephemeral per assignment. Fresh 96-bit nonce and 128-bit salt are generated by the operating-system CSPRNG. |
| Runner registration/API secrets | `secrets.token_urlsafe`, SHA-256 digests, `hmac`/`secrets.compare_digest` | One-time registration token and long-lived runner API secret | Plaintext is returned only when issued/registered; only SHA-256 digests are stored server-side. Registration token is cleared after successful registration. |
| Job/slice dispatch tokens | `secrets.token_urlsafe(32)` and constant-time comparison at the request boundary | Ephemeral dispatch token | Stored while an assignment is active and cleared on terminal/recovery paths. Used to derive the remote execution-data envelope key. |
| Fallback administrator password | Werkzeug `scrypt` password hashing | Human password | Only the scrypt hash is stored in the protected fallback hash file. |
| Browser session integrity | Flask/itsdangerous signing using `JOURNEYMAN_SECRET_KEY` | Deployment-specific signing secret | Production startup rejects an empty/default development secret. |
| Integrity fingerprints that are not secrets | SHA-256 | None | Used for content/configuration fingerprints and immutable snapshot verification; not used as password storage. |

## Key-management requirements

The credential key must be generated outside the repository, readable only by
the Journeyman service identity, and backed up separately from the database. A
database backup without the credential key must not be considered sufficient for
recovery; conversely, the credential key should not normally be stored in the
same backup artifact as the database.

Journeyman currently has one active Fernet credential key and does not yet expose
an online key-rotation/re-encryption workflow. Formal rotation, cryptoperiods,
retirement and emergency replacement remain pre-release security work. Until
that work exists, replacement of the credential key without re-encrypting stored
payloads will make those payloads unreadable.

## Crypto agility and future standards

Application code should keep cryptography behind narrow service interfaces so
algorithms can be replaced without changing every caller. The remote execution
envelope already declares an envelope version, algorithm and KDF. Credential
payloads carry a secret-format version at the model level, but a complete
credential-key rotation/migration mechanism is still required.

Post-quantum migration is not currently implemented. Before v1.0 or whenever
platform/vendor guidance materially changes, the cryptographic inventory must be
reviewed and migration work recorded before deprecated primitives are retained.
